# Safety Net — UI overhaul brief (prompt for Claude Design)

You're redesigning the single-screen web UI for **Safety Net**. Read the whole
brief, then produce the deliverable in §13. Where the brief gives a *visual*
suggestion, treat it as a floor you can improve on — but treat the
**constraints** (§11) and the **content/vocabulary** (§5–§8) as fixed.

## 1. What Safety Net is
A retrospective diagnostic-safety agent. It sweeps a backlog of finished
radiology reports, extracts every follow-up recommendation, and reasons about
whether each was **actually addressed** by a later study — not merely whether a
later study happened. Findings that fell through are surfaced, each with a
specific, human-answerable question. A capable scan that never mentions the
original finding is **UNCONFIRMED** and is escalated, never silently closed.

Current tagline on the page: *"Was the finding actually addressed — not just
whether a study happened."*

## 2. The one idea every pixel must serve
A later scan being **done** ≠ the original finding being **addressed**.
Incumbents match orders ("was a chest CT done? yes → case closed"). Safety Net
reasons about **acknowledgment** ("did that later scan actually re-evaluate the
nodule?"). The UI must make that distinction instantly legible: show the naive
"looks closed" read, then let the agent's reasoning visibly overturn it and
escalate with the exact question a clinician must answer. **That reveal is the
emotional core of the demo — design for it.**

## 3. Who sees it, and where
- A **live ~3-minute demo**, driven by a scripted ≤5-click path, shown on a
  **projector/large screen** to a room of judges.
- One judge is a **radiology-informatics domain expert whose former company
  ships a competing follow-up tracker.** The design must earn a skeptic's
  trust: clinical-grade, precise, restrained. Confidence without arrogance;
  precision over hype. No consumer-app flash.
- It is also **judged on Creativity and Execution**, so it must be visually
  distinctive and flawlessly finished — a considered *clinical instrument*, not
  a generic template.
- Every claim the agent makes carries a **verbatim citation** a clinician can
  verify in one click. Trust is built by making evidence visible, not by
  asserting confidence.

## 4. Current state (what you're improving)
Today the UI is a single self-contained `index.html` generated by a Python
script that injects the reconciliation data. It's a dark, minimal, single-column
stub: it works, but it's visually flat — undifferentiated cards, weak hierarchy,
no sense of the naive→reasoned reveal, and the "money-shot" moments (the
evidence highlight, the escalation question) don't stand out. Everything in §5
already renders; your job is to give it hierarchy, clarity, a point of view, and
demo-grade polish.

## 5. What's on the screen (component inventory + required states)
One page, top to bottom:

1. **Header** — product name + the tagline.
2. **Sweep bookend** — one small line: *"Swept N finished reports · X hero
   recommendation(s) reconciled."* This is a **two-second bookend for scale,
   deliberately not a dashboard** — keep it understated. (Bonus: a brief
   count-up on the opening "sweep" click.)
3. **Two hero cases**, each a section:
   - **Case header** — title; `patient name · patient id · as of <date>`; an
     italic one-line note.
   - For the recommendation in the case:
     - **Recommendation line** — the finding + its date; a sub-line with
       recommended modality/timeframe and the **naive date-logic status**
       (`OVERDUE` / `not overdue`). The naive status is the "incumbent view" the
       agent is about to complicate — make it feel like the obvious-but-wrong
       first read.
     - **Source report card** — the original report as monospaced clinical text,
       with the recommendation sentence **highlighted**.
     - **Candidate later-study card(s)** — the later report(s) as monospaced
       text, with the agent's **cited evidence highlighted**.
     - **Reasoning trace** — per candidate: a **verdict** + **confidence**, then
       the **five axes** (each: a result badge, a one-line reason, and verbatim
       citations tagged with their source id), then a **rationale**.
     - **Closure-state banner** — the aggregate outcome for the recommendation.
     - **Escalation block** *(Case A)* — a labelled callout: "needs a human
       answer" + the exact escalation question. **This is the single most
       important element on the screen.**
     - **Action + approval** *(Case A)* — a drafted patient/provider outreach,
       an **Approve** button, and, after approving, an **audit line** (approver ·
       timestamp · "logged to audit trail"). Human-gated: nothing sends itself.

## 6. The five reconciliation axes (and the crux)
Every candidate is scored on all five, in this order:
1. **Modality adequacy** — was the later scan the right *kind* of test?
   (`superior` / `pass` / `fail` / `unclear`)
2. **Anatomic coverage** — did it cover the right *place*?
   (`pass` / `fail` / `unclear`)
3. **Finding acknowledgment** — **THE CRUX.** Did the later report actually
   *mention / re-evaluate the specific finding*? Silence ≠ satisfaction.
   (`pass` / `fail` / `unclear`)
4. **Temporal adequacy** — was it done in time?
   (`on_time` / `late` / `never` / `unclear`)
5. **Terminal event** — a definitive closing event (e.g. benign PET/CT,
   biopsy). (`present` / `absent`, with a type)

**Finding acknowledgment gates the verdict.** Correct modality + anatomy +
timing but no acknowledgment → escalate. Give this axis visual weight so the
viewer's eye lands on it as the pivot — it is *why* Case A escalates and *how*
Case B is safely suppressed.

## 7. The two hero cases (use this real sample data in your mock)
**Case A — "looks closed, isn't" → ESCALATE.** Margaret Ellison · PT-A-2213 ·
as of 2026-07-18.
- Source (2024-10-08, CT chest w/o contrast): *"Solid 9 mm nodule in the left
  upper lobe, indeterminate… Recommend follow-up CT chest in 6 months."* Naive
  status: OVERDUE.
- Candidate (2025-03-18, CT angiogram chest, PE protocol): rules out PE, finds
  bronchitis — **never mentions the nodule.**
- Reasoning: modality **pass**, anatomy **pass**, **acknowledgment fail**,
  temporal roughly on_time, terminal absent → verdict **UNCONFIRMED** → closure
  **escalate**.
- Escalation question (this tone): *"A chest CT (PE protocol) was performed
  2025-03-18 but does not mention the left-upper-lobe nodule from 2024-10-08 —
  was the nodule reassessed? Confirm or deny."*
- Action: a drafted patient/provider outreach → Approve → audit line.

**Case B — "looks open, is closed" → SUPPRESS (superseded).** Harold Nkemelu ·
PT-B-7749 · as of 2026-07-18.
- Source (2024-06-15, CT chest w/o contrast): *"Indeterminate 11 mm solid nodule
  in the right middle lobe. Recommend follow-up CT chest in 3 months."* Naive
  status: OVERDUE (no matching follow-up CT).
- Candidate (2024-09-22, PET/CT skull base to mid-thigh): *"No hypermetabolic
  activity corresponding to the previously noted 11 mm right middle lobe nodule;
  findings favor a benign etiology."*
- Reasoning: modality **superior**, anatomy **pass**, acknowledgment **pass**,
  terminal **present (benign)** → verdict **SUPERSEDES** → closure
  **superseded**, **no escalation, no alarm.**

The two cases are a matched pair — the *same* capability catching a real miss
(A) and suppressing a false alarm (B). Design them so the contrast is obvious at
a glance: A resolves to a controlled **alert**; B resolves to a calm
**all-clear**.

## 8. Controlled vocabulary (label these exactly; build the color system around them)
- **Verdict:** SATISFIES · SUPERSEDES · PARTIAL · UNCONFIRMED · INADEQUATE ·
  NO_EVIDENCE
- **Closure state:** completed · superseded · declined · overrode ·
  open_overdue · escalate
- **Confidence:** high · medium · low
- **Axis results:** modality {superior, pass, fail, unclear}; coverage &
  acknowledgment {pass, fail, unclear}; temporal {on_time, late, never,
  unclear}; terminal {present, absent} + type {resolved, benign, biopsy,
  declined, overrode, none}

Group these into a **semantic set**: calm-good (satisfies, supersedes, pass,
superior, on_time, present, completed, superseded); attention-needed (fail,
never, open_overdue); a distinct **high-priority escalate / UNCONFIRMED** state
("a human must look" — not a generic error); and a cautionary third register
(unclear, partial, low confidence).

## 9. Visual direction (a strong starting point — improve on it; don't break §11)
- **Register:** a calm, high-trust *clinical instrument*. Generous whitespace,
  confident typographic hierarchy, restraint. "Modern medical software you'd
  trust," not "startup landing page."
- **Palette:** the current build is dark (near-black slate ground, ~`#0f1115`).
  Dark reads well on a projector and suits the tone; keep a dark foundation or
  offer a considered light option, grounded in **one confident accent** plus the
  disciplined semantic set from §8. **Don't rely on color alone** — pair every
  state with a label and/or icon/shape (a colorblind domain expert may be in the
  room, on a projector with unpredictable color).
- **Typography:** a clean UI sans for the interface; **monospace only for the
  verbatim report text**, so the clinical source reads as a document/evidence,
  distinct from the app chrome.
- **Evidence highlight:** the highlight on cited source text is a signature
  moment — make it feel like a clinician's highlighter landing on the exact
  words, and visually connect a citation in the reasoning trace to the
  highlighted span it came from. In Case A, make the *absence* of any highlight
  in the later report legible — the point is that the nodule is never mentioned.
- **The reasoning trace** should read as *thinking made visible*, not a data
  table — the five axes building to a verdict, with acknowledgment as the
  visible hinge.
- **The escalation block** is the hero element: it should command the screen
  when present — a **controlled alert that needs a human**, urgent but clinical,
  never a red error toast.

## 10. Interaction & motion (supports the live click-path)
The demo is a rehearsed sequence; support these moments, kept cheap and reliable
(this runs offline — see §11):
1. **Sweep** — opening state; a brief count-up to the swept / recommendation
   totals.
2. **Open Case A** → source report + the naive "looks closed" read.
3. **Run reconciliation** — a short (~1–2s) visible **"reasoning…"** state, then
   the trace renders. Latency reads as *the agent thinking* — lean into it with
   a considered reveal, not an instant pop.
4. **Open Case B** → reasoning renders → calm superseded / all-clear.
5. **Back to Case A → Approve** → audit line appears.

Motion should be subtle and quick — nothing that risks a live stumble or reads
as a gimmick to a skeptic.

## 11. Hard constraints (do not break these)
- **Single self-contained `index.html`.** Inline `<style>`, and only minimal
  vanilla JS if needed. **No build step, no frameworks, no external
  fonts/CDNs/network requests, no external assets** — it must render perfectly
  with **wifi off** (the demo has an offline fallback and judging rooms have
  unreliable wifi). Use system font stacks.
- **Ports back into a Python string-template renderer.** The real page is
  generated by a script that injects the data into this markup. Use **clean,
  stable, semantic class names** and a clear, repeatable per-section DOM
  structure (case → recommendation → report/candidate cards → axes → banner →
  escalation → action) so the markup maps back onto the generator with minimal
  churn. Keep it data-driven and repeatable, not hand-tuned per case.
- **Projector-legible:** high contrast; type large enough to read from the back
  of a room.
- **Content is fixed:** the sections, the five axes and their order, the
  vocabulary, and the citation-behind-every-claim principle are all part of the
  product's credibility — restyle and re-sequence for clarity, but don't drop
  them or invent new metrics.
- **Not a dashboard.** The sweep number is a two-second bookend, never the
  centerpiece. The **agent's reasoning is the hero.** (An analytics dashboard is
  an explicit anti-goal for this project.)

## 12. Non-goals
No login / nav / settings chrome, no charts or KPI tiles, no multi-page app, no
patient-list dashboard, no marketing hero section. One focused screen, two
cases, done impeccably.

## 13. Deliverable
1. A single self-contained **`index.html`** implementing the redesign, populated
   with the **Case A and Case B sample data above** so it demos as-is offline,
   and structured to port back into the Python renderer (§11).
2. A short **design rationale** (a few bullets): the point of view, the
   palette/type tokens (as CSS variables), and how you handled the
   evidence-highlight, the five-axis trace, and the escalation moment.
3. Optionally, note anything you'd refine with more time.

Start with the layout and the **Case A escalation reveal** — that's the beat the
whole demo turns on.
